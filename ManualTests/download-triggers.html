Test for bug 138673: MiniBrowser should support downloads for testing purposes.

Open this in a WK2 window, from file:// or over HTTP, either works. One thing that will look like a failure and is not: in a WK1 window steps 1 to 4 do nothing whatever the browser does with downloads, because the download attribute is off by default in legacy WebKit (DownloadAttributeEnabled in Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml).

Steps 5 and 7 use blob URLs on purpose. They are decided from the response rather than from the link, so they need a navigation the browser will really perform, and a top-frame navigation to a data: URL is refused whatever the response says — see disallowDataRequest in Source/WebCore/loader/DocumentLoader.cpp. Do not simplify them back to data:; both would then report the wrong result, the control loudest of all.

STEPS TO TEST: click every link and button below. None of them should navigate this page away, and none of them should show the file's contents inline.

TEST PASS: each of the six numbered steps saves a file, and the control link in step 7 navigates. Three of the files are named by the browser rather than by the test, so the expected set is: download-attribute.txt, blob.txt, Unknown.txt, from-script.txt, Unknown, Unknown-1.txt.

TEST FAIL: any step leaves the download folder unchanged, or replaces this page with the file's contents, or shows a blank page.

  1. download attribute, named — saves download-attribute.txt.
  2. download attribute on a blob: URL — saves blob.txt. The response here is synthesized by WebKit rather than coming from a server.
  3. download attribute, unnamed — saves a file whose name the browser picks, with a .txt extension taken from the MIME type.
  4. — saves from-script.txt. Same code path as step 1, but with no user click on the link itself.
  5. no download attribute, MIME type the browser cannot display — saves a file. A blob URL carries no filename and application/octet-stream implies no extension, so expect a browser-picked name with no extension, currently Unknown. That is what tells it apart from step 3's file. Here the decision comes from the response, not from the link, so it exercises a different delegate than steps 1 to 4.
  6. Right-click this link and choose Download Linked File — saves a file. This is a third code path again: the download is created by the context menu, with no policy decision involved.
  7. Control: no download attribute, MIME type the browser can display — must navigate and show its text, not download. If this one downloads, the fix is too aggressive.

Downloading a file whose name is already taken should also work: run step 1 twice and check that the second file is saved next to the first under a different name, rather than failing silently.

A response carrying Content-Disposition: attachment with a displayable MIME type is a further case that this page cannot cover, because it needs a server that sets the header. See bug 138673 for a page and a server command that do.
