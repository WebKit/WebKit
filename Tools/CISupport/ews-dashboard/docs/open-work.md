# Open work

This document tracks known gaps and planned work in this repository. It is kept here, rather than in an issue tracker, so a reader looking at the code can see in one place what is not done yet, why it matters, and what would make an obvious-looking fix wrong.

## Escape counting correctness

These affect the escape detector's numbers directly, and the first one should land before the others are worth chasing further, since it changes the shape of what the rest measure.

- **The landing-window and currency-window sentences on an escape row are not counted over comparable windows, and the currency window is not clamped to the landing.** `ews_dashboard/analysis/escapes.py`'s `check_currency` (around line 541) fetches runs from `now - CURRENCY_WINDOW_SECONDS` to `now` with no lower bound at the landing time, while the landing-window counts are taken strictly either side of `landed_at`. Because a stored row only reaches `ESCAPED` after a settling delay, the currency window can and does reach back past the landing, so `recent_runs` can exceed `runs_after` and the two sentences on the same row describe overlapping but different spans. The fix is to clamp the currency window's start to `max(candidate.landed_at, now - CURRENCY_WINDOW_SECONDS)`, which by construction restores `recent_runs >= runs_after`. Two riders belong in the same change: the window becomes variable-length, so a stored row needs to keep its own span rather than assuming the config constant; and the results.webkit.org page-size cap below has to be fixed alongside it, or `recent_failed` can still land under `failed_after` even with the window clamped.
- **The results.webkit.org runs endpoint returns at most `RUNS_PER_QUERY = 100` runs per response group** (`ews_dashboard/results.py:64`, passed as the endpoint's `limit` parameter at `:310`), **and that limit applies per configuration group in the response, not per query as a whole.** A window with more OS versions/models than fit under the cap silently drops the oldest runs in each group with nothing in the stored row to say so, so `recent_runs`/`runs_after` are floors that get tighter the wider the window. Needs either a higher limit or pagination of the endpoint.
- **Both count paths pool every OS version and model under one platform/style/flavor "configuration," not the specific queue a row is labelled with** (`ews_dashboard/results.py`, the `_runs_in`/`_fetch_runs` path, documented around line 252 onward). The queue name printed on an escape row is not the actual scope of the runs counted for it — it is every main bot sharing that platform/style/flavor.
- **`RUNS_SETTLING_SECONDS` is applied when reusing a stored verdict (`_stored`, `escapes.py` around line 489) but not by the counting or subcategory queries** (`_counted_verdicts` and `escape_subcategories`, `escapes.py`), so provisional verdicts sit in the same denominator as settled ones. On one local measurement this put the large majority of counted verdicts in the provisional state, with `CONTAINED` the bucket most likely to still flip to `ESCAPED`; treat the exact share as an order of magnitude, since it depends on the ingestion window measured.
- **The "still failing" / "recovered" read of the currency check applies no rate threshold at all**, unlike the landing-window escape grade. `currency_for_counts` (`escapes.py:152`) reads `STILL_FAILING` whenever `recent_failed` is truthy and `RECOVERED` otherwise, so one failure in a few hundred currency runs reads identically to a much higher rate. The 50% threshold that grades the landing window (`ESCAPE_FAILURE_PCT`, `config.py:33`) is never applied to the currency window.
- **The currency partition has a hole that prints as a recovery.** `currency_for_counts(recent_runs=1, recent_failed=None, recent_checked_at=100)` returns `RECOVERED`, because Python reads `None` as falsy in `STILL_FAILING if recent_failed else RECOVERED` — exactly the inference the module's own docstring says a currency answer must not make (an absence of evidence is not the same as a recovery). `schema.sql`'s `escape_verdicts` table declares `recent_runs`, `recent_failed` and `recent_checked_at` as three independently nullable columns with no `CHECK` tying them together, so "all three are null together, or none are" is a convention the write path (`_store_currency`) happens to honour rather than something the schema enforces. No row violates it today, as far as a local check could tell, but nothing stops one.
- **`escapes.py`'s candidate query interpolates the landed-status literal directly into SQL** (`landing.status = '{webkit_checkout.LANDED}'`, in the `CANDIDATE_SQL` string) **while the otherwise-equivalent `unaskable` query binds the same value as a parameter.** The value is not request-derived, so this is not a live injection risk, but it is the one interpolated literal in an otherwise fully-parameterized module and should be bound the same way for consistency.
- **`TREE_DIVERGED`'s "newest build of the pull request" lookup and the escape-counting queries already bound the newer build to `started_at <= landing.landed_at`** (`CANDIDATE_SQL` and the `convictions()` query in `escapes.py`) — this is fixed; an earlier version of this check had no upper bound and mis-attributed post-landing builds as divergence.

## Filters, sorting and the tests/escapes tables

The filter-and-sort rework has a strict build order: the column registry and canonical URL grammar had to exist (done) before any page could stop using the grammar it replaces, and each remaining stage below depends on the registry being in place, which it is (`ews_dashboard/analysis/filters.py`). What remains:

- The `find=`/`sort=`/`dir=` query parameters are gone; every page speaks the `f.<table>=column:op:value` / `s.<table>=column:direction` grammar now.
- **The escapes drilldown still caps its listing at `ESCAPES_LISTED = 200` (`escapes.py:112`, used as the default `limit` in `convictions()`) with no sort or paging control**, and the route serving it takes no sort/page arguments. A reader cannot see the remainder or reorder it.
- **The `/tests` and `/explore` pages' surfaced-tests list is still driven by a `test=` query parameter read in the templates** (`tests.html`, `explore.html`) rather than built server-side the way the rest of the filter grammar now is.
- **The escapes table has no horizontal scroll or sticky first column** — the corresponding fix already shipped for `/tests`, but `escapes.html`'s convictions table is not wrapped the same way, and `dashboard.css` has sticky-header rules but nothing pinning a leading column.
- **`ews_dashboard/web/static/dashboard.js` has grown to 432 lines** doing real progressive-enhancement work (widening chip controls without a page reload), which makes nine comments stale — `ews_dashboard/web/templates/tests.html:16` and `:80`, `ews_dashboard/web/templates/parts.html:110`, `ews_dashboard/web/templates/explore.html:83`, `ews_dashboard/web/chart.py:3` ("There is no JavaScript on any page of this dashboard", the flattest of them), `ews_dashboard/web/static/dashboard.css:747`, `:1251`, `:1356`, and `ews_dashboard/web/app.py:28-29` ("The freshness banner is dismissed by a request rather than in the browser, because this page needs no JavaScript and a dismissal has to hold on the next page too."). The rule was never "no JavaScript" — it is that every control stays answerable by a plain server-rendered submit with the script disabled. The `queue_dropdown` macro comment at `ews_dashboard/web/templates/parts.html:20-30` already states it correctly and is the model the other nine should copy.
- **The chart's hover target is still a 3px circle with no enlarged hit area**, and its container still carries `role="img"`, which makes its children presentational to assistive tech even though a `<title>` is present on the point. A transparent, larger hit circle plus dropping `role="img"` would fix both; this has not been checked in an actual browser.
- **The caveat sentence on the escapes page — "Undecided convictions are counted above, not dropped" — is unchanged.** On one local measurement over a 14-day window, a meaningful share of convictions were landed and resolvable with no stored verdict at all, and those appear in no tile on the page; the sentence is still accurate as far as it goes, but a fourth metric naming that group explicitly has not been added.

## Queue selection

The queue picker was rebuilt from a flat set of platform chips into a three-level collapsible tree (group, OS version, queue), because the flat chips undercounted: prefix matching like `LIKE 'macOS%'` missed suites such as `API-Tests-*`, and two platforms had no chip at all, leaving a large fraction of builds unreachable by any chip on a local measurement. The tree is in place (`ews_dashboard/web/templates/parts.html`, the `queue_dropdown` macro), with `aria-label`s on the otherwise-unlabelled group/version checkboxes and a comment on the macro that accurately describes its no-JS/with-JS split. Left to verify or finish, in no particular order since none blocks the others: ticking a parent should submit only the parent's own scope parameter rather than every builder it currently contains, so a queue added later stays covered; the `indeterminate` state on a partially-selected parent needs to be computed from server-rendered selection on page load, not only by script after a user click; and the checkbox should align to the top of an open group rather than drifting to its vertical middle. These were design decisions made before the rebuild and have not been individually re-confirmed against the current template.

## Ingest and refresh

- **The API-tests flakiness property gap is fixed and its yield understood: only builds after the property's own deployment carry it, so a re-ingest cannot retroactively supply history that was never recorded.** This is not an open item; recorded here because it explains why API-tests coverage looks sparse for any window that includes the deployment date.
- **`results-db_jsc_pre_existing` is still never read.** `ingest.py` only reads the first-run and second-run pre-existing properties; JSC builders are excluded from that path entirely by the negative-lookahead pattern in `suites.py:61` (`(?!JSC-)`), which exists because JSC's suite names cannot be told apart from the others by a simple prefix. Reading the JSC property needs its own path the way the API-tests fix above needed its own read, not a tweak to the shared pattern.
- `refresh.py`'s crash handling and its default window already match the widest window a page can request, and a fatal error record already retains the partial ingest count reached before the failure.
- `Tools/CISupport/ews-build/results_db.py`'s `WithinStepCleanTree` classification convicts on a single row with no pull-request or author threshold, and does not compare the evidence's PR numbers against the build's own, so a pull request's own earlier build can be read as proof its own failure predates it. This is EWS's own classification code, a sibling of this dashboard under `Tools/CISupport/`, not part of it, so the fix is a change there; local evidence for filing it is GTK-WK2-Tests-EWS build 153043.
- `config.py`'s `RULE_DESCRIPTIONS` text for `DirtyTree` states an author-count threshold that should track the one EWS's own classification code, `Tools/CISupport/ews-build/results_db.py`, actually enforces; this dashboard has not independently re-checked that the two numbers still agree, since the source of truth lives in that sibling tool rather than here.

## Miscellaneous

A UX review pass over the app found several smaller issues not yet addressed: a freshness-staleness banner that is dismissed by default rather than shown only when stale; provisional verdicts counted inside sets presented as decided; no remainder indicator when the escapes drilldown's cap truncates a list; page navigation that drops the current suite/builder selection when following certain links; a trend-chart day-bucketing note whose referenced constant no longer exists under that name in the code, worth re-deriving before trusting it; and a couple of small chart/label inconsistencies (an "all states" badge duplicating a separate "clear" control, gridline labels off by one step). None of these has been re-verified individually against the current templates; treat this paragraph as a punch list to re-derive from the running app rather than as confirmed findings.
